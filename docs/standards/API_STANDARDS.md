# API Standards

This document defines how the HTTP endpoints of this project are designed: URLs, HTTP methods and status codes, response format, pagination, versioning, caller identity, idempotency, export and limits. Each rule has an ID (such as `API-01`). Use this ID to refer to a rule in code review.

Error responses are not defined in this document. They are defined in `ERROR_AND_LOGGING_STANDARDS.md` (ERR-01 to ERR-08). OpenAPI documentation of endpoints is in `API_DOCUMENTATION_STANDARDS.md`.

To change a rule, open a PR that changes this file and write the reason in the PR description.

> **Status (1 November 2026):** All rules are applied in the code. Endpoints: `POST /v1/jobs`, `GET /v1/jobs`, `GET /v1/jobs/{id}`, `GET /v1/jobs/export.csv` (`src/modules/jobs/jobs.controller.ts`), `POST /v1/exports`, `GET /v1/exports/{id}`, `GET /v1/exports/{id}/file`, `DELETE /v1/exports/{id}` (`src/modules/job-exports/exports.controller.ts`), `POST` and `GET /internal/users/{id}/credits` (`src/modules/users/users.controller.ts`), `GET /health` (`src/modules/health`).

## Rule summary

| ID | Rule |
|---|---|
| API-01 | The API follows pragmatic REST: resource-oriented URLs, HTTP methods and status codes used according to their meaning. |
| API-02 | URLs use plural nouns in kebab-case and are nested at most one level. |
| API-03 | Each operation uses a specific HTTP method and status code. A job that completes later returns 202. |
| API-04 | A single record is returned directly. Lists are returned with `data` and `pagination` fields. |
| API-05 | Field names are camelCase, fixed list values are lowercase. Dates, IDs, credits and empty values use fixed formats. |
| API-06 | Endpoints for external clients start with `/v1`. `/health`, `/internal` and `/docs` are unversioned. A breaking change is made with a new version. |
| API-07 | Lists are paginated with a cursor and sorted newest to oldest. |
| API-08 | Filters use the field name and exact match. Unknown query parameters are rejected. There is no sort parameter. |
| API-09 | Every endpoint has a rate limit per client IP address and per endpoint. If Redis is down, the request is accepted. |
| API-10 | User endpoints identify the caller from the `X-User-Id` header. If the header is missing, 401 is returned. Another user's record appears as 404. |
| API-11 | A request that spends credits requires the `Idempotency-Key` header. A repeated request with the same key gets the first response and is not processed a second time. |
| API-12 | A large export response is written as a stream: memory stays constant, a slow client is waited for, reading stops when the connection drops. |
| API-13 | The number of unfinished jobs a user can have at the same time is limited (`MAX_ACTIVE_JOBS_PER_USER`). If the limit is exceeded, 429 is returned. |
| API-14 | `/health` returns 503 only if the database is down. If the cache Redis is down, it returns `degraded` and 200. |
| API-15 | Streamed exports run one per user and at most `EXPORT_MAX_CONCURRENT` across all instances. A request waits a few seconds for a slot, then gets 429 with `Retry-After`. |
| API-16 | A large export can be prepared in the background (Asynchronous Request-Reply): 202 with `Location` and `Retry-After`, the client polls, and a ready export answers 303 to its file. `EXPORT_MODE` decides which export the CSV path gives. |

## Design

### API-01: Pragmatic REST

**Rule:** A URL points to a resource (a job, a user's credits). The operation on the resource is expressed with the HTTP method, the result with the HTTP status code. Links to next steps are not added to responses (HATEOAS is not used).

**Why:** Most clients work with an HTTP library and `curl`. The resource, method and status code triple is the common language all these tools understand. Load balancers, logging and monitoring tools also look at the status code: to tell 4xx from 5xx, the error must be in the status code, not in the body. HATEOAS links make the response larger, and clients do not use them because they already know the URLs from the documentation.

**Check:** Code review.

### API-02: URL naming

**Rule:**

- A resource name is a plural noun written in kebab-case: `/v1/jobs`.
- URLs do not contain verbs. The operation is expressed with the HTTP method. Starting a job is done with `POST /v1/jobs`, not `/v1/jobs/start`.
- Nested URLs are at most one level deep: `/internal/users/{id}/credits`. Deeper relations are requested with query parameters.
- The job ID appears in the URL as a UUID v7 (`DATABASE_STANDARDS.md`, DB-03). The user ID is an external value not generated by this system: at most 64 characters, printable ASCII only (`src/core/auth/user-id.ts`).
- A representation of a resource in another format is written as a sub-path with a file extension: `GET /v1/jobs/export.csv`. This route is defined before the `:id` route, otherwise `export.csv` is taken as a job ID.
- Endpoints called only by internal systems start with the `/internal` prefix (SEC-09).

**Why:** All endpoints follow the same pattern, so a client can guess the address of a new endpoint. Deeply nested URLs break when the relation between resources changes. For export, an extension was chosen over an `Accept: text/csv` header, because the file must be downloadable from a link in a browser or with `curl -O` without writing a header. The `/internal` prefix lets internal endpoints be closed to the outside in production with a single path rule (gateway or load balancer).

**Example:**

| Correct | Wrong |
|---|---|
| `POST /v1/jobs` | `POST /v1/createJob` |
| `GET /v1/jobs?status=failed` | `GET /v1/jobs/failed` |
| `GET /v1/jobs/export.csv` | `GET /v1/exportJobs?format=csv` |
| `POST /internal/users/{id}/credits` | `POST /internal/users/{id}/add-credits` |

**Check:** Code review.

### API-03: HTTP methods and status codes

**Rule:**

| Operation | Endpoint in the project | Successful response |
|---|---|---|
| List | `GET /v1/jobs` | 200 and a list (API-04) |
| Single record | `GET /v1/jobs/{id}` | 200 and the record |
| Job that completes later | `POST /v1/jobs` | 202 and `{ jobId, status: "queued" }` |
| Increasing an existing value | `POST /internal/users/{id}/credits` | 200 and the new state of the record |
| File download | `GET /v1/jobs/export.csv` | 200 and a `text/csv` stream (API-12), or 202 and an export (API-16) |
| Work that produces a file later | `POST /v1/exports` | 202, `Location` and `Retry-After` (API-16) |
| Status of that work | `GET /v1/exports/{id}` | 200 while unfinished, 303 to the file once ready |
| Cancelling it | `DELETE /v1/exports/{id}` | 200 and the export with status `canceled` |

- `POST /v1/jobs` returns 202, not 201: the job was accepted but not yet done. The client queries the result with `GET /v1/jobs/{jobId}`.
- Adding credits returns 200, not 201, because it does not create a new resource, it increases the balance. That the user record is created on the first addition is an internal detail.
- Today there are no update endpoints. If added, a partial update uses `PATCH` and returns 200 with the new state of the record. A delete that removes the record uses `DELETE` and returns 204. `DELETE /v1/exports/{id}` returns 200 with the export instead, because it cancels the work and the export stays readable with status `canceled`; a finished export is returned unchanged.
- Business rule errors return their own status codes: insufficient credits 402 `INSUFFICIENT_CREDITS`, the same key used with a different request 422 `IDEMPOTENCY_KEY_REUSED`, a credit grant past the INTEGER maximum 422 `BALANCE_LIMIT_EXCEEDED`, too many unfinished jobs 429 `TOO_MANY_ACTIVE_JOBS`, an export already running for the user 429 `EXPORT_IN_PROGRESS`, no free export slot 429 `EXPORT_SLOTS_BUSY`. The error response format and the other codes are in `ERROR_AND_LOGGING_STANDARDS.md`, ERR-01 to ERR-03.

**Why:** The status code decides how the client handles the response. 202 tells the client "do not wait for the result, ask later". A job can take seconds, so keeping the request open ties up both the client and the server. 402, meaning "payment required", states insufficient credits directly and is enough to send the client to the credit top-up screen. 429 has several causes (API-09, API-13, API-15), and the client tells them apart with the `code` field.

**Check:** Code review. NestJS returns 201 for `POST` by default. Other codes are set with `@HttpCode`.

### API-04: Response format

**Rule:** An endpoint that returns a single record returns the record directly. An endpoint that returns a list returns an object with two fields: `data` (the records) and `pagination` (API-07). Success is not written in the response body, it is read from the HTTP status code. The response is always produced from a response DTO (`SECURITY_STANDARDS.md`, SEC-06).

A list returns the fields needed for the list, not all fields of the record. `GET /v1/jobs` does not carry the result (`result`) of each job. The result is fetched only with `GET /v1/jobs/{id}`.

**Why:** For single records, an envelope is an unnecessary layer. For lists, pagination information must be carried next to the records. Fields like `success: true` repeat the HTTP status code. A job's result can be a long text. Carrying all results in a page of 100 records makes the response larger and also causes unnecessary reads from the database.

**Example:**

```json
GET /v1/jobs/0192f3a1-7c4e-7b2a-9d1f-3e5a8b6c2d10
200
{
  "jobId": "0192f3a1-7c4e-7b2a-9d1f-3e5a8b6c2d10",
  "type": "summary",
  "status": "completed",
  "errorCode": null,
  "cost": 3,
  "createdAt": "2026-10-30T08:00:00.000Z",
  "finishedAt": "2026-10-30T08:00:02.512Z",
  "result": "..."
}
```

```json
GET /v1/jobs?limit=20
200
{
  "data": [
    { "jobId": "0192f3a1-7c4e-7b2a-9d1f-3e5a8b6c2d10", "type": "summary", "status": "queued", "errorCode": null, "cost": 3, "createdAt": "2026-10-30T08:00:00.000Z", "finishedAt": null }
  ],
  "pagination": { "nextCursor": "MDE5MmYzYTEtN2M0ZS03YjJhLTlkMWYtM2U1YThiNmMyZDEw", "hasMore": true }
}
```

**Check:** Code review.

### API-05: Field names and value formats

**Rule:**

| Value | Format | Example |
|---|---|---|
| Field name (body and query parameter) | camelCase | `errorCode`, `finishedAt` |
| ID field of the resource | `<resource>Id`, not `id` | `"jobId"`, `"userId"` |
| Date and time | ISO 8601, UTC, with milliseconds | `"2026-10-30T08:00:00.000Z"` |
| Credit | Integer, JSON number | `"cost": 3`, `"balance": 7` |
| Job ID | UUID string | `"0192f3a1-7c4e-7b2a-9d1f-3e5a8b6c2d10"` |
| Fixed list value | Lowercase, underscore | `"status": "queued"`, `"errorCode": "provider_timeout"` |
| Field with no value | The field is present in the response, its value is `null`. | `"finishedAt": null` |

In an error response, `code` is uppercase and the `error` field is its lowercase form (`ERROR_AND_LOGGING_STANDARDS.md`, ERR-01, ERR-02). The job's `errorCode` field is a fixed list value and is lowercase: it is not an HTTP error, it is the outcome stored in the job's record.

**Why:** camelCase is the native field name format of JavaScript and mobile clients. The client uses the response without converting it. Database fields stay snake_case (`DATABASE_STANDARDS.md`, DB-02), so the response DTO maps the fields. This mapping is required anyway, because a Prisma record is not returned directly (`SECURITY_STANDARDS.md`, SEC-06; `CODING_STANDARDS.md`, CODE-03). Naming the ID field `jobId` makes the same value appear under the same name in the `POST` response, in the list and in the single record. A credit is not money, it is an indivisible unit. It is an integer and stays far below 2^53, so it is carried as a JSON number without loss of precision. Fixed list values are also stored in lowercase in the database (DB-09), so no value conversion is needed. Because fields are always present in the response, the client does not need to handle "field missing" and "value empty" separately.

**Check:** Code review. Response DTOs are written with these formats.

### API-06: Versioning

**Rule:** Endpoints called by external clients start with `/v1`. This is set up in `src/core/http/configure-http.ts` with NestJS URL versioning. Controllers do not declare a version, the default version is used.

Three groups of paths are unversioned. The first two are marked with `VERSION_NEUTRAL` in the controller:

- The infrastructure endpoint `/health`. The load balancer and orchestrator know this address as a fixed value.
- Internal endpoints `/internal/...` (SEC-09). Their clients are our own internal systems and change together with the API.
- The API documentation: Swagger UI at `/docs` and the OpenAPI file at `/docs/openapi.json` (`API_DOCUMENTATION_STANDARDS.md`, DOC-05). They are not controllers; they are set up in `src/core/http/openapi/openapi.ts`.

A breaking change is not made on an existing `/v1` endpoint. A new version of the endpoint (`/v2`) is written, and the old version runs alongside it for a while.

| Breaking, needs a new version | Not breaking, done in the same version |
|---|---|
| Removing a field from the response or renaming it | Adding a new field to the response |
| Changing the type or format of a field | Adding a new endpoint |
| Adding a required field or header to the request | Adding an optional field to the request |
| Changing the meaning of a status code or error code | Adding a new fixed list value (if the client tolerates unknown values) |
| Removing a column from the CSV file or changing column order | Adding a column at the end of the CSV file |

**Why:** Clients whose old releases stay in use for a long time, such as mobile apps, must keep working without an update when the API changes. The version is in the URL, so it is visible at once in logs, in the browser and in the documentation. Adding a version to internal endpoints opens a compatibility layer that nobody would use between two systems that change together.

**Check:** Infrastructure. `configureHttp` is used by both `main.ts` and the e2e tests, so the tests run with the real URLs.

## Lists

### API-07: Cursor pagination

**Rule:** List endpoints are paginated with a cursor. Pagination uses the shared schema and helpers in `src/core/http/pagination.ts`.

- The client sends `limit` and, optionally, `cursor`. `limit` defaults to 20 and can be between 1 and 100. A value out of range is not clamped, it is rejected with 400.
- The `pagination` field in the response contains `nextCursor` and `hasMore`. On the last page, `nextCursor` is `null` and `hasMore` is `false`. The total record count is not returned.
- The order is newest to oldest: `id` descending. Job IDs are UUID v7, so `id` order matches creation order (`DATABASE_STANDARDS.md`, DB-03). `id` is unique, so records created at the same moment are not lost or repeated across pages.
- The cursor is the base64url-encoded `id` of the last record on the page. To the client it is a meaningless (opaque) string. The client does not try to decode or build the cursor. A cursor that cannot be decoded is rejected with 400.
- The query reads `limit + 1` records. The extra record only shows whether a next page exists and is not added to the response. So `hasMore` needs no separate count query.
- Each list query has an index that starts with the filter fields and ends with `id` descending: on the `jobs` table, `(user_id, id DESC)` and `(user_id, status, id DESC)`.

**Why:** With page numbers (`OFFSET`), the database reads all skipped records again for later pages and gets slower as the table grows. If a new job is added between pages, the same record appears twice. New records are added to the top of the job list all the time, so this problem really happens here. The cursor method fetches every page at the same speed using the index. The total count is not returned, because for a user with millions of jobs `COUNT` scans the table on every page, and the client's "is there more" question is answered by `hasMore`.

**Example:**

```
GET /v1/jobs?limit=20
GET /v1/jobs?limit=20&cursor=MDE5MmYzYTEtN2M0ZS03YjJhLTlkMWYtM2U1YThiNmMyZDEw
```

```json
{ "data": [], "pagination": { "nextCursor": null, "hasMore": false } }
```

**Check:** Code review. The query schema is extended from `CursorPaginationQuerySchema`, the response is built with `pageOf` and `pageSchemaOf`, and the filter with `afterCursor`.

### API-08: Filtering and sorting

**Rule:**

- **Filter:** The query parameter name is the name of the field in the API, and it does an exact match: `GET /v1/jobs?status=failed`.
- **Allowed fields:** The filters of each endpoint are defined one by one in the query schema (`CursorPaginationQuerySchema.extend(...)`). The schema is a `strictObject`, so an unknown parameter is rejected with 400, `VALIDATION_FAILED` and a per-field `UNKNOWN_FIELD` (`ERROR_AND_LOGGING_STANDARDS.md`, ERR-04).
- **Empty value:** A query parameter sent with an empty value (`?status=&limit=&cursor=`) counts as not given and gets its default. `ZodValidationPipe` drops empty values of `@Query` input before validation, so this holds for every endpoint.
- **Sorting:** There is no sort parameter. The order is always as in API-07.
- A new filter is added only together with an index that covers it (`DATABASE_STANDARDS.md`, DB-08).

**Why:** All list endpoints use the same format, so the client does not learn separate rules for each endpoint. Rejecting unknown parameters prevents a misspelled filter (`?stauts=failed`) from being silently ignored and the whole list from being returned. Free sorting was not added: the cursor would have to carry every sort field too, and each sort order would need its own index. Today no client asks for a different order.

**Check:** Code review. Query parameters are validated with `ZodValidationPipe` (`CODING_STANDARDS.md`, CODE-11). `test/jobs.e2e-spec.ts` (empty query parameters).

## Rate limit

### API-09: Rate limit

**Rule:** Every endpoint applies a rate limit per client IP address and per endpoint. The default limit is 1000 requests per minute. If the limit is exceeded, the response is 429 with the `TOO_MANY_REQUESTS` error code and a `Retry-After` header (`ERROR_AND_LOGGING_STANDARDS.md`, ERR-01). Successful responses carry the `X-RateLimit-Limit`, `X-RateLimit-Remaining` and `X-RateLimit-Reset` headers.

| Setting | Default | Description |
|---|---|---|
| `RATE_LIMIT_TTL_SECONDS` | 60 | Counter window (seconds) |
| `RATE_LIMIT_MAX` | 1000 | Number of requests allowed in the window |
| `TRUST_PROXY_HOPS` | 0 | Number of proxies in front of the application. When 0, the `X-Forwarded-For` header is ignored. |

- Counters are kept in the cache Redis, so a single counter is used even when the application runs on more than one server. Incrementing the counter and the block decision happen in one step, in a single Lua script.
- If Redis cannot be reached, the request is not rejected, it is allowed. This is logged at most once per minute with `RATE_LIMIT_STORAGE_UNAVAILABLE` (`CACHE_STANDARDS.md`, CACHE-07).
- IPv6 addresses are counted per /64 network. So different addresses from a single network cannot bypass the limit.
- `/health` is excluded from the limit with `rateLimited: false` in `@ApiEndpoint` (`API_DOCUMENTATION_STANDARDS.md`, DOC-01).
- If the application runs behind a load balancer or reverse proxy, `TRUST_PROXY_HOPS` is set to the number of proxies. If it is not set, all clients appear to come from the proxy's IP address and share a single counter. If it is enabled without a proxy, a client can bypass the limit by writing the header itself.

**Why:** The rate limit makes it harder for a single client to slow down the API and to pull data in bulk. A limit per IP and per endpoint prevents a client's heavy use of one endpoint from cutting off its access to the other endpoints. The default is 1000, because clients track job status by polling a single endpoint (`GET /v1/jobs/{id}`) often, and a lower limit also blocks legitimate clients. Rejecting requests while Redis is down turns a failure of the protection layer into a failure of the whole API. Staying unlimited for a short time does less harm. The main protection against spending credits is not this limit, it is the per-user job limit (API-13).

**Check:** Infrastructure. `ThrottlerGuard` is applied to all endpoints (`app.module.ts`). Endpoint test: `test/rate-limit.e2e-spec.ts`.

## Identity and repetition

### API-10: Caller identity and record ownership

**Rule:**

- All endpoints under `/v1/jobs` are protected by `UserIdGuard`. The caller is identified from the `X-User-Id` header (`src/core/auth`). If the header is missing or invalid (empty, longer than 64 characters, non-printable characters), the response is 401 and `USER_ID_REQUIRED`.
- Authentication is not in the scope of this project. The correctness of the header is the responsibility of an authentication layer (gateway) in front of it.
- The service adds the `user_id` condition to every query. Another user's job, a job that does not exist, and an ID that is not in UUID format all get the same response: 404 `JOB_NOT_FOUND`. 403 is not returned.
- The controller takes the ID with `@UserId()` and passes it to the service as a parameter. The service does not read the ID from the request itself.

**Why:** Authentication is out of scope, but because a guard reads the identity in one place, only the guard changes when real authentication is added, not the services. Returning 403 reveals "a job exists with this ID but it is not yours" and makes it easier to find job IDs by trying them. 404 is the same in every case, so nobody outside can tell whether an ID exists. Passing the ID to the service as a parameter lets the same service also be called from the queue, without an HTTP request.

**Example:**

```
GET /v1/jobs/0192f3a1-7c4e-7b2a-9d1f-3e5a8b6c2d10   (no X-User-Id)  → 401 USER_ID_REQUIRED
GET /v1/jobs/0192f3a1-7c4e-7b2a-9d1f-3e5a8b6c2d10   X-User-Id: user-2 (job belongs to user-1) → 404 JOB_NOT_FOUND
GET /v1/jobs/not-a-uuid                             X-User-Id: user-1 → 404 JOB_NOT_FOUND
```

**Check:** Code review and endpoint tests (`test/jobs.e2e-spec.ts`).

### API-11: Idempotency-Key on requests that spend credits

**Rule:** A request that spends credits (`POST /v1/jobs`) requires the `Idempotency-Key` header.

- If the header is missing or longer than 255 characters, 400 `VALIDATION_FAILED` is returned. The error appears in the `errors` list with the field `Idempotency-Key`, like other field errors.
- The key is per user: the same key used by two users does not affect each other.
- A request with the same key and the same body within 24 hours is not processed again. The first request's response is returned: 202 and the same `jobId`. The `status` in the response is always `queued`, even if the job has finished in the meantime. The current status is fetched with `GET /v1/jobs/{id}`.
- If the same key comes with a different body, 422 `IDEMPOTENCY_KEY_REUSED` is returned. The body is compared by the raw values of the `type` and `input` fields.
- Concurrent requests with the same key create a single job and a single credit reserve. The second request waits in the database until the first one finishes and gets the first job's ID.
- A rejected request (for example 402) does not store the key. After topping up credits, the user can retry with the same key.
- A key older than 24 hours is handled like a new request. Expired keys are deleted in the background in small batches.

**Why:** On a mobile network, a request can reach the server and the response can get lost. When the client retries, without a key the user would be charged twice. The client must generate the key, because only the client knows what "the same request" is: on the server, sending the same text twice on purpose cannot be told apart from a retry. Storing the key in the same transaction as the job, its content and the reserve makes an in-between state such as "the key was stored but the job was not created" impossible. Rejecting a key that comes with a different body prevents a client bug (the same key for every request) from silently getting a wrong response. 24 hours is much longer than the time in which retries end in practice, and short enough to keep the table from growing without limit.

**Example:**

```
POST /v1/jobs  Idempotency-Key: 7f3c...  { "type": "summary", "input": "..." }  → 202 { "jobId": "0192f3a1-...", "status": "queued" }
POST /v1/jobs  Idempotency-Key: 7f3c...  { "type": "summary", "input": "..." }  → 202 { "jobId": "0192f3a1-...", "status": "queued" }  (credits are not deducted again)
POST /v1/jobs  Idempotency-Key: 7f3c...  { "type": "translate", "input": "..." } → 422 IDEMPOTENCY_KEY_REUSED
```

**Check:** Endpoint tests (`test/jobs.e2e-spec.ts`): repeat, different body, another user, expired key, retry after 402, and 10 concurrent requests with the same key.

## Export

### API-12: A large export is written as a stream

**Rule:** `GET /v1/jobs/export.csv` writes all of the caller's jobs as CSV, newest to oldest (`src/modules/job-exports`).

- **Memory:** Records are read and written in batches of 1000 (`EXPORT_BATCH_SIZE`). No matter how many jobs the user has, at most one batch is in memory.
- **Slow client (backpressure):** If `response.write()` returns `false`, the `drain` event is awaited before the next batch is read. Data is not pulled from the database faster than the client can read it.
- **Short queries:** Each batch is a separate, short query (`id < last id`, using the index). No long-lived database cursor or transaction is opened. While the client waits, no connection, lock or snapshot is held.
- **Connection drop:** The response's `close` event stops the loop. The batch query running at that moment finishes, and no new query starts. A response that is already closed (`destroyed` or `writableEnded`) does not wait for `drain`, and an export whose client left before it started stops at once.
- **Mid-stream error:** If an error occurs after the headers are sent, the connection is cut (`response.destroy`). The response is not closed cleanly, so the client does not take a partial file as complete. In this case an RFC 9457 body cannot be sent.
- **Consistency:** The file is not a snapshot of a single moment. Each batch shows the state at the time it was read. Jobs created after the export starts do not get into the file, because reading moves from the newest ID to older ones.
- **Format:** RFC 4180: values with a comma, quote or line break are quoted, and every record, the header included, ends with CRLF (`\r\n`). Columns `job_id,type,status,cost,error_code,created_at,finished_at`. The file does not contain the job text or its result. A value that could run as a formula in a spreadsheet (starting with `=`, `+`, `-`, `@`) is prefixed with `'`.

**Why:** A user can have millions of jobs. Loading all of them into memory and sending them at once crashes the process with out-of-memory under a few concurrent exports. Streaming makes memory independent of the record count. A long-lived database cursor would give a single consistent snapshot, but a slow client would keep a connection and a transaction open for minutes. An open transaction blocks PostgreSQL from cleaning up old row versions (vacuum), and the frequently updated `jobs` table bloats. For a job list, "each row as it was when read" is enough, so short queries were chosen. Formula escaping prevents running commands on the computer of the person who opens the file (CSV injection), if user text is added to the columns later.

**Check:** Unit tests (`job-csv.spec.ts`; `job-export.service.spec.ts`: the client leaves during a batch or before the start) and endpoint test (`test/jobs.e2e-spec.ts`).

The same row writer (`JobExportService.writeRows`) writes the HTTP response and the file of a background export (API-16), so both have the same format, memory profile and backpressure.

### API-15: Concurrent streamed exports are limited

**Rule:** A streamed export holds two things while it runs (`src/modules/job-exports/export-admission.service.ts`):

- **A per-user lock** in the cache Redis. A second streamed export of the same user gets 429 `EXPORT_IN_PROGRESS` at once, with `Retry-After: 10`.
- **A permit** from a shared pool of `EXPORT_MAX_CONCURRENT` (default 200) for all API instances: a sorted set in Redis whose members expire unless renewed (`CacheService.acquirePermit`, a Lua script on Redis time). The holder renews the permit and the lock every 10 s and releases both when the response ends; a crashed instance's permits expire after 30 s.
- A request without a permit asks again every 100–500 ms (random), up to `EXPORT_ADMISSION_WAIT_MS` (default 10 s). Then it gets 429 `EXPORT_SLOTS_BUSY` with `Retry-After: 10`. A client that disconnects while waiting stops the wait at once.
- **Redis down:** the per-user lock is skipped and each instance allows `EXPORT_FALLBACK_MAX_CONCURRENT` (default 20) streamed exports with an in-process semaphore, under the same wait and 429.

**Why:** A streamed export holds a database connection for every batch and runs for as long as the client reads. Without a limit, many users exporting at once take every connection in the pool, and job creation and reads fail for everyone. The limit is global and leased, not a fixed share per instance, because the number of instances changes and a crashed instance must not keep its share. The short wait absorbs a burst, and `Retry-After` turns the rest into a retry instead of a queue of open connections. One export per user is enough: the file is the same, and a client that retries in a loop cannot take many slots. The fallback keeps a limit during a Redis outage: the database is what the limit protects, so "no Redis" must not mean "no limit".

**Check:** Unit tests (`export-admission.service.spec.ts`: lock, wait, timeout, disconnect, fallback), database tests (`cache.service.db-spec.ts`: permits) and endpoint test (`test/job-exports.e2e-spec.ts`: 429 and `Retry-After`).

### API-16: Background exports (Asynchronous Request-Reply)

**Rule:** `POST /v1/exports` accepts an export of all of the caller's jobs and returns 202, the export, `Location: /v1/exports/{id}` and `Retry-After: 5` (`src/modules/job-exports`).

- The export row and its outbox row are written in one transaction, and a worker writes the file (`JobExportRunService`, QUEUE-01, QUEUE-08). The worker claims the export with a lease and a `lock_token` like a job (DB-15), retries a failure up to 3 attempts with backoff, and the worker's maintenance timer requeues an export whose worker died and re-sends one no worker received.
- `GET /v1/exports/{id}` returns 200 and the export while it is `queued` or `processing` (with `Retry-After`), 303 with `Location: /v1/exports/{id}/file` once `ready`, and 200 with `failed`, `canceled` or `expired` otherwise.
- `GET /v1/exports/{id}/file` streams the file (`text/csv`) while the export is ready and its file has not expired (`EXPORT_FILE_TTL_MS`, default 24 h, judged by the database clock). Otherwise 404 `EXPORT_FILE_NOT_FOUND`.
- `DELETE /v1/exports/{id}` cancels an unfinished export. A worker writing it loses its lease and stops; its file is never marked ready.
- A user has at most one unfinished export (a partial unique index). A second request returns that export, and a request within 5 minutes of a ready one returns the ready one, both with 202.
- Another user's export and a malformed id are 404 `EXPORT_NOT_FOUND` (API-10).
- `EXPORT_MODE` decides what `GET /v1/jobs/export.csv` gives: `stream` (default) streams it (API-12, API-15); `async` answers as `POST /v1/exports`; `auto` streams when the user has at most `EXPORT_STREAM_MAX_ROWS` (default 10,000) jobs and answers 202 otherwise.
- Files are kept by a `FileStore` (`src/infra/file-store`). Today the only one writes to a directory (`EXPORT_FILES_DIR`), a Docker volume shared by the API and the workers. A file is written to a temporary name and renamed when complete, so a partial file is never served.

**Why:** A streamed export of 500,000 jobs ties a connection and a permit to the client's speed: a phone on a slow network holds both for minutes, and a dropped connection starts over. Preparing the file once in the background bounds the database work by the workers (`EXPORT_WORKER_CONCURRENCY` per worker), whatever the number of requests, and the download is then a plain file that a CDN or object store could serve. 202 with `Location` and `Retry-After` is the standard form of this pattern, so a client needs no special knowledge to follow it; 303 sends the client to the file with a `GET`, whatever method it used. Reusing an unfinished or recent export makes a retry or a double tap free. `auto` keeps the common case simple (most users have few jobs and get their file at once) and moves only the heavy exports off the request path. `stream` is the default because it is what the case asks for and needs no file storage.

**Check:** Unit test (`export-plan.spec.ts`) and endpoint tests (`test/job-exports.e2e-spec.ts`: 202 and headers, reuse, 303 and file, poll, 404s, cancel, shutdown before the claim, expiry, maintenance).

## Job limit and health

### API-13: Per-user unfinished job limit

**Rule:** A user can have at most `MAX_ACTIVE_JOBS_PER_USER` (default 50) unfinished jobs at the same time. If the limit is exceeded, `POST /v1/jobs` returns 429 and `TOO_MANY_ACTIVE_JOBS`. This response has no `Retry-After` header.

- The counter is the `users.active_job_count` column. It is incremented in the same `UPDATE` statement as the credit reserve, with the condition `active_job_count < limit`. It is decremented when the job finishes (successfully or not).
- If credits are insufficient, 402 takes precedence. 429 is returned only if credits are sufficient but the limit is full.

**Why:** An IP limit does not stop a user: the user can send requests from many addresses, and if credits are sufficient, thousands of jobs enter the queue. This delays other users' jobs and spends provider calls on a single user. Checking the limit in the same statement as the credit reserve prevents two concurrent requests from both taking the last free slot. `Retry-After` is not written, because it is not known when the jobs will finish. A wrong duration makes the client wait for nothing or retry too early.

**Check:** Endpoint test (`test/jobs.e2e-spec.ts`).

### API-14: Health check

**Rule:** `GET /health` returns the status of the database and the cache Redis. It does not require an identity header and is excluded from the rate limit and the request logs.

| State | `status` | HTTP |
|---|---|---|
| Everything is up | `ok` | 200 |
| Only the cache Redis is down | `degraded` | 200 |
| The database is down | `error` | 503 |

Kafka is not part of this check. The API does not connect to Kafka: jobs are written to the outbox table and sent by the worker (`QUEUE_STANDARDS.md`, QUEUE-08).

**Why:** A load balancer takes a server that returns 503 out of traffic. Without the database the API cannot serve any request, so 503 is correct. Without the cache Redis, requests keep working (the rate limit is turned off temporarily, CACHE-07). Returning 503 in this case would take all servers out of traffic at the same time and turn a small failure into a full outage. The `degraded` state is enough for monitoring tools to raise an alert.

**Check:** Unit tests (`health.service.spec.ts`, `health.controller.spec.ts`) and endpoint test (`test/health.e2e-spec.ts`).

When writing a new controller or a new endpoint on an existing controller, all of the steps below are applied. The list only refers to the rules. The full rules are in their own files. The same list is also checked when the behavior of an endpoint changes.

| Step | Rule |
|---|---|
| 1. Choose the URL and HTTP method. `/v1` for external clients, `/internal` for internal systems. | API-02, API-03, API-06, `SECURITY_STANDARDS.md`, SEC-09 |

## Technical details

**Rate limit:** The official NestJS `@nestjs/throttler` package (6.7.1) is used. The key is made of the controller name, the method name and the client IP address, so the counter is per endpoint. The Redis storage is in `src/infra/cache/redis-throttler.storage.ts`. The ready-made `@nest-lab/throttler-storage-redis` package was not used because it does not state support for NestJS 12. The settings are built in `src/core/http/rate-limit.options.ts` and combined with the Redis storage in `app.module.ts`, so the `core` layer does not import the `infra` layer (ARCH-02).

NestJS applies the limit after it finds a matching route. A request to a route that does not exist returns 404 without going through the limit check.

**Request ID:** Every response carries the `x-request-id` header. If the client sends a `traceparent` header, its trace id value is used (`ERROR_AND_LOGGING_STANDARDS.md`, LOG-01).
