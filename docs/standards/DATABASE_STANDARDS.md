# Database Standards

This document defines the rules to follow when working with PostgreSQL and Prisma. Each rule has an ID (such as `DB-01`). Use this ID to refer to a rule in code review.

To change a rule, open a PR that changes this file and write the reason in the PR description.

> **Status (1 November 2026):** The rules are applied in the code. PostgreSQL 17, Prisma 7.10.1 and `@prisma/adapter-pg` are used. The schema is split into modules under `prisma/schema/` (`users.prisma`, `jobs.prisma`). Everything the Prisma schema cannot express (CHECK constraints, partial indexes, column compression, initial configuration rows) is in the SQL files under `prisma/migrations/`.

## Rule summary

| ID | Rule |
|---|---|
| DB-01 | Model names are singular and PascalCase. Table names are plural and snake_case. |
| DB-02 | Field and column names are snake_case in both code and the database. |
| DB-03 | The primary key of entity tables is a UUID v7 generated by the application. Configuration tables use a code, and identities from outside use their own value. |
| DB-04 | Every table has `created_at`. Tables whose rows are updated also have `updated_at`. The type is `timestamptz(3)`. |
| DB-05 | `deleted_at` is not used. Tables that carry history are not deleted from. Temporary tables are deleted from in batches when rows expire. |
| DB-06 | Credit is an integer (`Int`). The amount is always positive. Its direction comes from the entry type. `Float` is not used. |
| DB-07 | Every relation states `onDelete` explicitly. All relations are `Restrict`. |
| DB-08 | Every foreign key column has a plain index. A partial index does not replace this index. |
| DB-09 | Closed lists that database logic depends on are PostgreSQL enums. Growing lists are text. Lists that change at runtime are tables. |
| DB-10 | Dropping or renaming a column or table is done in two phases. |
| DB-11 | Services use `PrismaService` directly. No repository layer is written. The service that owns the flow opens a transaction that spans several modules. |
| DB-12 | Raw SQL is written only with `$queryRaw` and `$executeRaw`, as a template literal. |
| DB-13 | A new table is not added to the schema before its scope is clarified with the product owner. |
| DB-14 | Writes that read and decide are done with a single conditional SQL statement. The affected row count gives the result. |
| DB-15 | Ownership of a long-running job is held with a lease (`locked_until`) and an ownership token (`lock_token`). Every write by the owner includes the token as a condition. |
| DB-16 | All transactions run with `Read Committed`. Rules that look at several rows are expressed with a counter column or a unique index. |
| DB-17 | External services are not called inside a transaction. The only exception is the outbox relay. |
| DB-18 | A migration file that has been applied to a shared database is not changed. |
| DB-19 | Migrations are applied only by `prisma migrate deploy`, and only in a separate step. |
| DB-20 | Each migration contains one coherent change. Schema and data are in separate migrations. |
| DB-21 | Time comparisons use the database clock (`now()`). For a value written with the application clock, clock skew must not change the result. |
| DB-22 | Data rules are also written in the database as CHECK constraints and unique indexes. |
| DB-23 | The credit balance changes only together with a ledger entry, in the same SQL statement. The ledger is append-only. |
| DB-24 | A job that must not be repeated claims a unique key in its first step with `INSERT ... ON CONFLICT DO NOTHING`. |
| DB-25 | Batch jobs that run in several processes take rows with `FOR UPDATE SKIP LOCKED`, in limited batches. |
| DB-26 | List queries are paginated with a cursor. `OFFSET` is not used. The query's index is verified with a realistic data volume. |
| DB-27 | Frequently updated rows do not hold large text. The text lives in a separate, shared table. |

## Naming

### DB-01: Model name singular, table name plural

**Rule:** A Prisma model name is singular and PascalCase (`Job`, `JobTypeRoute`). The table name in the database is plural and snake_case (`jobs`, `job_type_routes`). The two are mapped with `@@map`. Tables whose name is already a collective noun do not take a plural suffix (`UserCreditLedgerEntry` → `user_credit_ledger`). A module's tables start with the module's name (`job_*`), so the owner of a table is clear from its name (`ARCHITECTURE_STANDARDS.md`, ARCH-06).

**Why:** A model represents a single record, so it is singular. A table is the set of records. snake_case table names need no quotes in SQL. This matters because raw SQL is written often in this project (DB-12).

**Example:**

```prisma
model JobTypeRoute {
  // ...
  @@map("job_type_routes")
}
```

**Check:** Code review.

### DB-02: Field and column names are snake_case everywhere

**Rule:** Field names in a Prisma model are snake_case. The column name in the database is the same as the field name, so `@map` is not used. Relation fields are also snake_case (`credit_ledger`, `job_provider`).

**Why:** A column has one name in the code, in the database and in raw SQL queries. A column name in raw SQL does not need to be translated to a Prisma field.

**Example:**

```prisma
model Job {
  job_content_id String @db.Uuid
  content        JobContent @relation(fields: [job_content_id], references: [id], onDelete: Restrict)
}
```

**Check:** Code review.

**Effect:** Field names in objects returned by Prisma and in raw SQL rows are snake_case. API fields are camelCase (`API_STANDARDS.md`, API-05). The mapping is done in the function that builds the response DTO (`toJobDto`) or in the function that converts a raw SQL row (`toJob`) (`CODING_STANDARDS.md`, CODE-03).

### DB-09: Closed lists are enums, growing lists are text, changing lists are tables

**Rule:** There are three ways to define the values a column can take:

| List | Way | Example |
|---|---|---|
| Closed, database rules depend on it | Prisma enum (PostgreSQL enum type) | `job_status`, `job_result_source`, `user_credit_entry_type` |
| Grows with the code, no database rule depends on it | `VarChar`, values are constants in code | `jobs.error_code` (`JobFailureCode`) |
| Added and removed at runtime | Separate table, code is the primary key | `job_types`, `job_providers` |

The enum name is PascalCase and is mapped to a snake_case PostgreSQL type with `@@map`. Values are lowercase with underscores (`queued`, `processing`).

**Why:** An enum prevents invalid values from being written, and CHECK constraints and partial indexes can safely depend on it (`status <> 'failed' OR error_code IS NOT NULL`, `WHERE status = 'processing'`). The cost is that every new value needs a migration. For lists such as status, which rarely change and are part of database rules, the cost is worth it.

Error codes, however, grow with every new error case. Writing a migration for each one ties a code change to a database change, and while different versions of the API and worker run at the same time (DB-10), the old schema rejects the value the new version writes. No database rule looks at the value of an error code, so text is enough.

Job types and providers carry price, limit and weight, and must be changeable without a deploy. That is why they are tables, not enums.

**Example:**

```prisma
enum JobStatus {
  queued
  processing
  completed
  failed

  @@map("job_status")
}
```

**Note:** An enum value cannot be removed if rows use it. Before removing a value, the two-phase method in DB-10 is applied. Adding a value (`ALTER TYPE ... ADD VALUE`) is possible, but the new value cannot be used until the transaction that adds it commits. The migration that adds the value and the data change that uses it are written in separate migrations.

**Check:** Code review.

## Columns

### DB-03: Application-generated UUID v7 in entity tables

**Rule:** The primary key is chosen by table kind:

| Table kind | Primary key | Tables |
|---|---|---|
| Entity (records that grow over time) | `id`, UUID v7, `@db.Uuid` | `jobs`, `job_contents`, `user_credit_ledger`, `job_outbox_messages` |
| Configuration (few rows, referred to by name from code) | `code`, `VarChar` | `job_types`, `job_providers` |
| Identity from outside | The incoming value | `users.id` (`X-User-Id` header, `VarChar(64)`) |
| Natural composite key | Composite `@@id` | `job_type_routes`, `job_idempotency_keys` |

The application always generates the UUID v7 value: `uuidV7()` in `src/shared/uuid-v7.ts`. For rows inserted with raw SQL, the `id` is given in the query (`${uuidV7()}::uuid`). `@default(uuid(7))` in the schema is only a fallback for calls that write through Prisma and do not give an `id`. The database has no default value for `id`.

**Why:**

- **Why UUID v7.** Adding a new key to a B-tree index is cheap if the key falls at the end of the index: the same last page always stays in memory. UUID v4 is random, so each insert goes to a random page of the index. Once the table reaches millions of rows and the index no longer fits in memory, each insert means a disk read and frequent page splits. The first 48 bits of a UUID v7 are the time in milliseconds, so v7 keys are appended at the end like an auto-increment number.
- **Why not a number.** An auto-increment number lets someone guess the total job count and neighbouring IDs from an ID in a URL. It is also known only after the write to the database. UUID v7 carries 74 bits of randomness and can be generated in advance.
- **Why the application generates it.** The job ID is needed before the job row is written: the idempotency key is claimed with this ID in the first step (DB-24). The seed (`src/seed.ts`) generates past-time IDs for backdated records (`uuidV7(createdMs)`). A single generator also leaves no difference between raw SQL and Prisma.
- **Time order comes free.** The ID sorts by creation order, so the "newest jobs" list is read with the `(user_id, id DESC)` index, without a `created_at` index (DB-26).
- **Why not in every table.** Configuration tables are referred to by name from code (`summary`), and jobs copy this code. A separate UUID would need one more mapping on every read. The user ID does not belong to us: authentication is out of scope for this project, and the sender of the header decides its format.

**Note:** UUID v7 reveals the record's creation time with millisecond precision. For jobs this is not a problem, since `createdAt` is already returned in the response. Two IDs generated in the same millisecond in different processes may not sort in creation order. This precision is enough for listing.

**Check:** Code review. The `id` column of a new entity table is `@db.Uuid` and is given by the application.

### DB-04: created_at in every table, updated_at in tables whose rows are updated

**Rule:** Every table has `created_at`. Tables whose rows are updated also have `updated_at`. Both have the type `timestamptz(3)` (with time zone, millisecond precision). Only append-only tables, or tables whose rows are only inserted and deleted, have no `updated_at`:

| Table | `updated_at` | Why |
|---|---|---|
| `user_credit_ledger` | No | Append-only (DB-23). |
| `job_idempotency_keys` | No | Inserted, and deleted when expired. |
| `job_outbox_messages` | No | Its only change is writing `sent_at`, and that column already carries the time of the change. |

The `@updatedAt` value is written by Prisma Client, not by the database. Every raw SQL query that updates a row writes `updated_at = now()` itself.

**Why:** When a record was created and when it last changed are the first questions asked during debugging and incident review. In a row that never changes, `updated_at` always equals `created_at`: it takes space and tells nothing. Leaving this column out of the ledger also makes the rule "this row does not change" visible in the schema.

A `timestamp` without time zone does not record which time zone the value was written in. When the server's or the connection's time zone changes, the same value points to a different moment. `timestamptz` always stores the same moment. The precision is milliseconds, the precision of JavaScript `Date`. More precision would make a value read from the database and written back not equal to itself.

**Example:**

```prisma
created_at DateTime @default(now()) @db.Timestamptz(3)
updated_at DateTime @updatedAt @db.Timestamptz(3)
```

```sql
UPDATE jobs SET status = 'completed', ..., updated_at = now() WHERE ...
```

**Check:** Code review. Look for `updated_at` in raw SQL `UPDATE`s.

### DB-05: No deleted_at, history is not deleted, temporary records are deleted when they expire

**Rule:** No table uses `deleted_at`. Tables fall into two groups:

| Group | Tables | Deletion |
|---|---|---|
| History | `jobs`, `job_contents`, `user_credit_ledger`, `users` | The application does not delete. |
| Temporary | `job_idempotency_keys` (24 hours), `job_outbox_messages` (1 hour after sending) | A background job permanently deletes expired rows in batches (DB-25). |

**Why:** History tables carry the trail of money: if a job's record is deleted, the row that explains its ledger entry is lost and the balance cannot be recomputed from the ledger (DB-23). `Restrict` relations (DB-07) also prevent this at the database level.

`deleted_at` forces a filter on every query, and a single forgotten filter shows a deleted record. In this project there is no record that must be deleted and still kept.

Temporary tables are not allowed to grow without limit. The idempotency table grows by one row for each job created. At a scale of 10 million users, rows that are never deleted keep raising the cost of the index and of vacuum. Deletion is done in batches (for example 1,000 rows), because a `DELETE` that removes millions of rows at once holds locks for a long time, produces a lot of WAL and leaves replicas behind.

**Check:** Code review. When a new table is added, the DB-13 scope note states which group the table belongs to.

### DB-06: Credit is an integer

**Rule:** Credit amounts are stored as `Int` (PostgreSQL `INTEGER`): `job_types.cost`, `jobs.cost`, `users.balance`, `users.reserved` and `user_credit_ledger.amount`. The ledger `amount` is always positive (`CHECK (amount > 0)`). The direction of the entry is set by `entry_type` (`grant`, `reserve`, `capture`, `release`). `Float` and `Decimal` are not used for credit.

The job's price is copied to `jobs.cost` when the job is created. Reserve, capture and release always use this value, not the current price in the configuration.

**Why:** Credit is an indivisible unit defined by the product: a summary costs 3 credits, a translation 1, and there is no half credit. An integer expresses this definition exactly:

- Arithmetic is exact. `Float` makes rounding errors. `Decimal` needs objects and conversion on every calculation for a precision this project does not need.
- Prisma returns `Int` as a JavaScript `number`, and it is lossless as long as the value stays below 2³¹. The upper limit of a single grant is 1,000,000 (`MAX_GRANT_AMOUNT`).
- CHECK constraints (`balance >= 0`) and conditional updates (`balance >= cost`) compare directly in the database.

Keeping the amount always positive makes entries with unclear meaning, such as "a negative reserve", impossible. The balance formula (DB-23) takes the direction from the type.

Copying the price to the job prevents the price of an accepted job from changing later through a configuration change. Otherwise the reserved and captured amounts could differ and the `reserved` column would not return to zero.

**Note:** If real money (buying credits) is added, money amounts do not fall under this rule. The amount type and currency for that table are decided separately in the DB-13 process.

**Check:** Code review. The CHECK constraints are in the migration.

## Relations and indexes

### DB-07: onDelete is explicit, all relations are Restrict

**Rule:** Every relation states `onDelete` explicitly. All relations in this project are `onDelete: Restrict`: a parent record cannot be deleted while dependent records exist. `Cascade` is not used.

**Why:** Prisma uses `Restrict` for required relations and `SetNull` for optional ones. This difference is not visible from the schema. Writing the value explicitly makes delete behaviour visible on every relation.

No child record is a part that must be deleted together with its parent. Deleting a user would delete their jobs, deleting jobs would delete ledger entries, and the money history would be lost (DB-05). `SetNull` silently makes a ledger entry forget which job it belongs to. `Restrict` prevents, at the database level, an accidental delete from taking thousands of rows with it.

**Example:**

```prisma
user User @relation(fields: [user_id], references: [id], onDelete: Restrict)
```

**Note:** Since `onUpdate` is not written, foreign keys are created with Prisma's default `ON UPDATE CASCADE`. Configuration codes (`job_types.code`, `job_providers.code`) are not renamed. If one is renamed, this rewrites every dependent row in the `jobs` and `job_contents` tables in a single transaction. If a code change is needed, a new code is added and the old one is disabled (`is_enabled = false`).

**Check:** Code review.

### DB-08: Every foreign key column has a plain index

**Rule:** There is an index for every foreign key column. If the column is already the first column of a primary key, a `@@unique` or a composite index, no separate index is needed. Example: for `jobs.user_id`, the `(user_id, id DESC)` index is enough. A partial index (with a `WHERE` condition) does not replace this index.

**Why:** PostgreSQL does not add indexes to foreign key columns automatically. When a parent record is deleted or its key changes, PostgreSQL checks the child table for dependent rows. Without an index, this check scans the whole child table. So in a ledger with millions of rows, even deleting a single job can take minutes.

A partial index cannot be used for this check, because the check query does not include the index's condition. The `user_credit_ledger` table has two partial unique indexes on `job_id` (DB-23), but it still has a plain `job_id` index. This is written in the comment in `users.prisma` and in the migration.

**Example:**

```prisma
model UserCreditLedgerEntry {
  job_id String? @db.Uuid
  job    Job?    @relation(fields: [job_id], references: [id], onDelete: Restrict)

  @@index([job_id])
  @@map("user_credit_ledger")
}
```

**Check:** Code review.

## Schema changes

### DB-10: Drops and renames are done in two phases

**Rule:** Dropping or renaming a column, table or enum value is not done in a single migration. The change is split into phases released in separate versions:

1. The new column is added. The code writes to both the old and the new column. Old data is copied to the new column.
2. The code reads and writes only the new column.
3. The old column is dropped.

**Why:** The API and the worker are separate processes and are updated separately. During a deploy, the old and new versions run at the same time for a while. Messages sent by the old version may also be waiting in Kafka. If a column is dropped or renamed in one step, the old code that is still running fails. In the worker, this means jobs get stuck with their reserved credit.

**Example:** Renaming the `jobs.error_code` column to `failure_code` takes three versions. The first version adds the `failure_code` column and writes to both columns. The second version uses only `failure_code`. The third version drops the `error_code` column.

**Check:** Code review. If a migration file contains `DROP` or `RENAME`, the reviewer checks that the earlier phases have been released.

### DB-18: A migration applied to a shared database is not changed

**Rule:** After a migration has been applied to a shared database (test environment, staging, production), its file is not edited or deleted. If a fix is needed, a new migration is written.

Migrations that have not reached any shared database can be rewritten. Before delivery, this project merged and simplified its unreleased migrations this way. The current files under `prisma/migrations` are the base of the first release. Every change from now on is a new migration.

**Why:** Prisma stores a checksum of every applied migration in the `_prisma_migrations` table. A changed file causes an error in environments that have run that migration. Worse, if the change is silently not applied, the environments' schemas drift apart and the same code behaves differently in different environments. A migration that nobody has run yet has no such risk. There, keeping broken steps to preserve history only creates clutter.

**Check:** Code review. If a PR changes an existing file under `prisma/migrations`, it is questioned.

### DB-19: Migrations are applied only by migrate deploy, in a separate step

**Rule:** The schema of shared databases changes only through `prisma migrate deploy`. `prisma migrate dev` and `prisma db push` are used only on the developer's own database. The schema is not changed with manual SQL in the database.

Migrations run once, in a separate step, before the application and the worker start. The `migrate` service in `docker-compose.yml` runs `prisma migrate deploy` and exits. The `app`, `worker` and `seed` services wait for this service to finish successfully. The `CMD` line of the application image only starts the application. The test database is set up with the same command (`test/support/global-setup.ts`).

**Why:** `migrate dev` and `db push` can perform operations that delete data. A manual change does not enter the migration history and is not repeated in other environments.

If the application ran migrations on startup, all API and worker instances starting at the same time would try to apply the same migration. A failed migration would also put every instance into a restart loop. A separate step separates migration failure from application failure: if the migration fails, the new version never starts and the old version keeps running. Using the same command in tests makes tests run on the same schema as production.

**Check:** `Dockerfile` (`CMD`) and `docker-compose.yml` (the `migrate` service and the `depends_on` conditions).

### DB-20: Each migration contains one coherent change

**Rule:** A migration makes one change that makes sense as a whole: a table with its constraints, indexes and foreign keys, or a small group of related tables (`add_job_config_tables`). A migration that inserts data is separate from a migration that changes the schema (`insert_initial_job_config`). The migration name describes the change and is snake_case.

**Why:** If a migration fails in production, its name tells which change caused the problem, and only that change is handled. Separating a table from its constraints is risky the other way: between the two migrations the table has no constraints. Keeping the data migration separate makes the location of the problem clear if the schema is set up correctly but the data insert fails.

The initial configuration rows (job types, prices, provider) are not sample data. They are part of the schema: the API rejects an unknown job type. So they are in a migration, not in the seed script, and every new installation starts with them.

**Example:**

- Correct: `add_jobs_table`, `insert_initial_job_config`
- Wrong: `jobs_and_cleanup`, `update`

**Check:** Code review.

## Usage in code

### DB-11: Services use PrismaService directly

**Rule:** Code that accesses the database is written in the service class of the module that owns the table and uses `PrismaService` directly. No separate repository layer is written. Controllers do not use `PrismaService`.

In a flow that writes the tables of several modules in one transaction, the service that owns the flow opens the transaction and decides the order. The services of the other modules offer methods that take this transaction as a parameter (`tx: Prisma.TransactionClient`). Each module writes only to its own tables (`ARCHITECTURE_STANDARDS.md`, ARCH-06).

**Why:** Prisma Client is already a type-safe data access layer. A repository on top of it needs extra code for every query and hides the real cost of the query (which index, how many rows) behind one more layer.

The transaction boundary is a business decision: "These changes happen together or not at all." The owner of the flow makes this decision. For example, in job creation `JobsService` decides the order: it first reads the user (`requireUser`, no lock), then claims the idempotency key as the first write (DB-24), and locks the user's row last (DB-14). The owner of a table knows how to write it: the credit rules are in `UsersService`, the idempotency rules are in `JobIdempotencyService`.

**Example:**

```ts
// JobsService: owns the flow, opens the transaction
await this.prisma.$transaction((tx) => this.createInTransaction(tx, job), {
  isolationLevel: Prisma.TransactionIsolationLevel.ReadCommitted,
});

// UsersService: writes its own table inside the given transaction
async reserveCredits(tx: Prisma.TransactionClient, reservation: CreditReservation): Promise<void> { ... }
```

**Check:** Code review.

### DB-12: Raw SQL only with safe syntax

**Rule:** Raw SQL is written only with `$queryRaw` and `$executeRaw`, as a tagged template. `$queryRawUnsafe` and `$executeRawUnsafe` are not used. Reused parts of a query are written with `Prisma.sql` (`CLAIMABLE`, `JOB_COLUMNS`).

Raw SQL is used in these cases, because the Prisma API cannot express them:

- Updates where the condition and the change are in one statement and the result is returned with `RETURNING` (DB-14)
- `WITH ... UPDATE ... INSERT`, which writes an update and a ledger entry in the same statement (DB-23)
- `INSERT ... ON CONFLICT DO NOTHING` (DB-24)
- `FOR UPDATE SKIP LOCKED` (DB-25)
- Times computed with the database clock (`now() + make_interval(...)`, DB-21)

Raw SQL skips Prisma's automatic values. The query gives the `id` (DB-03) and `updated_at` (DB-04) values itself. Parameters are cast explicitly (`${jobId}::uuid`, `${cost}::int`).

**Why:** Values given in a template literal go to the database as parameters and do not become part of the SQL. In the `Unsafe` methods, values are inserted into the SQL text. If the value comes from the user, this opens an SQL injection hole.

The explicit cast is needed because the driver sends the parameter as text and PostgreSQL cannot infer the type in some contexts (`CASE`, `UNION`, function arguments). The cast moves the error from runtime to the test where the query is first tried.

**Example:**

```ts
// Correct
await tx.$queryRaw`SELECT id FROM jobs WHERE id = ${jobId}::uuid AND user_id = ${userId}`;

// Wrong
await tx.$queryRawUnsafe(`SELECT id FROM jobs WHERE id = '${jobId}'`);
```

**Check:** Code review. Every method that contains raw SQL is tested against a real database (`TESTING_STANDARDS.md`, TEST-04).

## Concurrency and transactions

### DB-14: A write that reads and decides is a single conditional statement

**Rule:** In operations that decide based on a row's value and change that row (reserving balance, claiming a job, writing a result once), the check and the change are done in a single SQL statement. The condition goes in the `WHERE`. The affected row count (or the row returned by `RETURNING`) is the result of the decision: if it is 0, the condition was not met. Reading first and then writing in a separate statement is forbidden.

The method is chosen in this order:

1. **Single conditional statement.** `UPDATE ... WHERE <condition> RETURNING ...` or Prisma `updateMany({ where: { ..., <condition> } })`.
2. **Unique index.** If the rule is "at most one", the index decides (DB-24, DB-23).
3. **Lease and token.** If the row must be held for the length of a long job (DB-15).
4. **`FOR UPDATE SKIP LOCKED`.** In batch jobs where several processes share work from the same list (DB-25).

A blocking `SELECT ... FOR UPDATE` (one that waits for the lock) is not used.

If a transaction locks several rows, the most contended row is locked last. In job creation this is the user's row: `reserveCredits` is the last statement of the transaction.

**Why:** If reading and writing are separate statements, two requests read the same balance and both find it sufficient. If a user with a balance of 5 starts two 3-credit jobs at the same time, both are accepted.

This cannot happen in a single statement: the second `UPDATE` waits for the row lock. At `Read Committed`, when the first one commits, PostgreSQL reads the new version of the row and evaluates the `WHERE` condition again. The new balance is 2, so the condition is not met and the second request gets 0 rows. No extra lock, retry or higher isolation is needed.

The user's row is the single point where all of that user's requests queue up. If it is locked at the start of the transaction, the lock is held for the rest of the transaction (content insert, job insert, outbox), and the same user's other requests wait that long. If it is locked at the end, the lock is held only until commit.

**Example:**

```sql
-- UsersService.reserveCredits (shortened)
WITH reserved AS (
  UPDATE users
     SET balance = balance - ${cost}::int, reserved = reserved + ${cost}::int,
         active_job_count = active_job_count + 1, updated_at = now()
   WHERE id = ${userId} AND balance >= ${cost}::int AND active_job_count < ${maxActiveJobs}::int
  RETURNING id
)
INSERT INTO user_credit_ledger (id, user_id, job_id, entry_type, amount)
SELECT ${uuidV7()}::uuid, id, ${jobId}::uuid, 'reserve', ${cost}::int FROM reserved
RETURNING id
-- 0 rows: insufficient credit or too many open jobs
```

```ts
// Wrong: two requests can read the same balance
const user = await tx.user.findUniqueOrThrow({ where: { id: userId } });
if (user.balance < cost) throw insufficientCredits();
await tx.user.update({ where: { id: userId }, data: { balance: user.balance - cost } });
```

**Check:** Code review. Code that reads a row and updates the same row based on the value read is questioned. `test/jobs.e2e-spec.ts`: of five concurrent 3-credit requests from a user with a balance of 5, at most one is accepted.

### DB-15: Ownership in a long-running job is held with a lease and a token

**Rule:** If a process will "hold" a row for a long time outside a database transaction (such as the worker sending a job to a provider), ownership is written to the row itself:

1. **Claim.** A single conditional `UPDATE` (DB-14) writes a random `lock_token` and `locked_until = now() + lease duration` to the row.
2. **Heartbeat.** The owner extends the lease at regular intervals. The extension also includes `lock_token` as a condition. If it returns 0 rows, ownership is lost and the job is stopped.
3. **Finish.** Every write by the owner includes the condition `WHERE id = ... AND lock_token = <token> AND status = 'processing'`. If it returns 0 rows, nothing is written and no credit operation is done (`JOB_LEASE_LOST`).
4. **Takeover.** A job is taken from its owner only after its lease has expired (`locked_until < now()`), in one of two ways. A worker's claim (step 1) can take it directly, because the claim condition (`CLAIMABLE`) also matches `status = 'processing' AND locked_until < now()`, and the claim writes a new token. Or the reconciler puts it back on the queue and clears the token.

Today there is no record that users edit through the API. If such a record is added, optimistic locking with a `version` column is used against two clients editing the same record: the update is done with the condition `WHERE version = <read>`, `version` is incremented by one, and 0 rows returns 409.

**Why:** A provider call takes seconds. Keeping a database transaction and a row lock open for that time exhausts the connection pool (DB-17). When the lock is kept in the database itself, as a column, no transaction is needed.

A lease alone is not enough. A worker whose lease has expired but which does not know it (one returning from a long pause, or one that lost its network) may try to finish the job. Meanwhile the job has been given to another worker. The token (fencing token) makes the late write of the old owner ineffective: the token has changed, so the condition is not met and nothing changes. So a job is not completed twice and its credit is not captured twice. This gives the certainty that a Redis lock (`CACHE_STANDARDS.md`, CACHE-12) cannot.

The lease duration and the reconciler's check are computed with the database clock (DB-21), because only one clock must decide ownership.

**Example:**

```sql
-- JobLifecycleService.complete
UPDATE jobs
   SET status = 'completed', ..., lock_token = NULL, locked_until = NULL, updated_at = now()
 WHERE id = ${jobId}::uuid AND lock_token = ${lockToken}::uuid AND status = 'processing'
RETURNING user_id, cost
```

Background exports (`job_exports`) use the same three columns and the same steps (`JobExportRunService`). A user's cancel clears the token, so the worker's next heartbeat finds no row and stops writing.

**Check:** Code review. `test/job-processing.e2e-spec.ts`: a worker that lost the job writes nothing; a job whose worker died returns to the queue. `test/job-exports.e2e-spec.ts`: a canceled export is not prepared; an export whose worker died returns to the queue.

### DB-16: Isolation level Read Committed

**Rule:** All transactions run with `Read Committed`, the PostgreSQL default level. `Serializable` and `Repeatable Read` are not used. A rule that looks at several rows is reduced to a single-row decision in one of these ways:

| Rule | Way | Example |
|---|---|---|
| "At most N" | A counter on the owner's row, incremented and decremented with a conditional update | `users.active_job_count < MAX_ACTIVE_JOBS_PER_USER` |
| "At most one" | Unique or partial unique index | One reserve and one capture per job (DB-23) |
| "Same request once" | Claim with a unique key | Idempotency key (DB-24) |

A transaction conflict or deadlock (Prisma `P2034`) is not retried automatically. It returns 409 with the `CONFLICT` code. The client retries with the same `Idempotency-Key`. The worker's result write (`JobSettlementService.settle`), however, retries briefly on its own on a database error, because at that point there is a provider response that has already been paid for.

**Why:** `Serializable` protects rules that look at several rows by itself, but the cost is high: it keeps lock records for every range read, cancels transactions that have no real conflict as concurrency grows, and requires every caller to write a retry loop. In a system like this project, which writes heavily to the same user row, the cancel rate rises under load and retries raise the load further.

A counter column gives the same protection more cheaply: instead of counting open jobs with `COUNT(*)`, the counter is checked and incremented in the same conditional `UPDATE` as the balance (DB-14). The check is not an index scan. It looks at a single row that is already locked. A unique index also guarantees the "at most one" rule without retries.

**Check:** Code review. `isolationLevel` only takes the value `ReadCommitted`.

### DB-17: External services are not called inside a transaction

**Rule:** Only database operations are done inside `$transaction`. Provider (AI) calls, Redis and HTTP calls are done before or after the transaction. A Kafka message that results from a database change is written to the outbox table in the same transaction as the change (`JobOutboxService.enqueue`) and sent after the transaction (`QUEUE_STANDARDS.md`, QUEUE-08).

The only exception is the outbox relay (`JobOutboxRelayService.relayBatch`). The relay locks unsent rows with `FOR UPDATE SKIP LOCKED`, sends them to Kafka, and after Kafka acknowledges, writes `sent_at` in the same transaction. This exception holds within these limits:

- The transaction locks only outbox rows. No other request waits for these rows.
- Time is limited: the Kafka send timeout is 10 seconds, the transaction timeout is 15 seconds (`OUTBOX_RELAY_TIMEOUT_MS`).
- A Kafka message can arrive more than once, and the consumer tolerates this.

**Why:** External operations cannot be undone. If the transaction fails, a sent message cannot be pulled back and a paid provider call cannot be reversed. If the external service is slow, the transaction gets longer, the row locks it holds make other requests wait, and it keeps a pool connection busy. Provider calls take seconds, so if they were made inside a transaction, the number of jobs processed at the same time would be limited by the size of the connection pool.

The outbox removes the cases "data was written but the message was not sent" and "the message was sent but the data was rolled back": the message is committed together with its data, or not written at all.

The relay's exception is a deliberate choice. Both alternatives are worse: marking a row "sent" before sending loses the message if the send fails. Sending without holding a lock lets two relays send the same row at the same time. The locked rows are shared only by relays, so the lock is cheap, and the time limit makes it known how long the connection stays busy.

**Example:**

```ts
// Wrong: the transaction waits for the provider response
await this.prisma.$transaction(async (tx) => {
  const text = await provider.generate(...);
  await this.contents.saveResult(tx, content.id, text);
});

// Correct: call first, then result, status and credit in one transaction
const outcome = await this.resolver.resolve(request);
await this.prisma.$transaction((tx) => this.apply(tx, settlement));
```

**Check:** Code review. Check that every call `await`ed inside `$transaction` goes to the database.

## New table process

### DB-13: The scope of a new table is clarified first

**Rule:** If a change seems to need a new table, the questions below are answered together with the product owner before a model is added to the schema and a migration is created. Claude asks the user these questions and does not change the schema until the answers are clear.

| Topic | Question |
|---|---|
| Need | Which business need does the table meet? Is adding a column to an existing table enough? |
| Owner | Which module owns the table? (`ARCHITECTURE_STANDARDS.md`, ARCH-06) |
| Fields | Which fields are there? What is each field's type, is it required, and what is its default value? Which rules must be CHECK constraints? (DB-22) |
| Key | Is it an entity, configuration, or an identity from outside? (DB-03) |
| Relations | Which tables is it related to? What happens if the parent record needs to be deleted? (DB-07) |
| Lifecycle | History or temporary? If temporary, how long is it kept and who deletes it? (DB-05, DB-25) |
| Credit and money | Does it contain a credit or money amount? Does it change the balance? (DB-06, DB-23) |
| Concurrency | Will several processes or requests change the same row at the same time? (DB-14, DB-15) |
| Sensitive data | Does it contain personal or sensitive data? (`ERROR_AND_LOGGING_STANDARDS.md`, LOG-07) |
| Usage | Which fields will the table be queried by most? How many rows will it have at 10 million users? How often is a row updated? (DB-08, DB-26, DB-27) |

The answers are written in the PR description as a short scope note.

**Why:** Once a table is in production, changing its structure needs a two-phase migration (DB-10). Changing a column type or adding an index on a table with millions of rows can take hours. Clarifying the scope up front prevents unneeded tables and risky changes later.

**Check:** Code review. A PR that adds a new table contains a scope note.

## Time

### DB-21: Time comparisons use the database clock

**Rule:** Every time comparison in SQL uses the database clock (`now()`). Times that decide ownership or duration are computed in the database: the lease (`locked_until = now() + ...`), the idempotency key expiry (`expires_at = now() + ...`), a retry's delay (`run_after = now() + ...`, returned and reused as the outbox row's `not_before`), and the selections of the reconciler and cleanup jobs (`locked_until < now()`, `expires_at <= now()`).

If a value written with the application clock is compared with the database clock, a few milliseconds or seconds of difference between the two clocks must not make the result wrong. In this project, the values written with the application clock are:

| Value | Source | Why it is not a problem |
|---|---|---|
| `created_at`, `run_after`, `dispatched_at`, `not_before` in rows inserted through Prisma (`@default(now())`) | Prisma Client, application clock | A new job's `run_after` is never checked (see below). The others are compared only on a scale of seconds or minutes. |
| `job_contents.result_at` | `new Date()` | Not compared in any query. |

The job claim condition (`CLAIMABLE`) does not look at `run_after` for jobs that have never been tried (`attempt_count = 0`). `run_after` is only for delaying retries.

**Why:** The API, the worker and the database run on separate machines, and their clocks are not exactly the same. If the two sides of a comparison come from different clocks, clock skew turns directly into a bug. Example: if the API's clock is 5 ms ahead of the database's, a new job's `run_after` value is 5 ms in the future for the database. The Kafka message arrives at once, the worker finds the condition `run_after <= now()` not met and skips the message. The job waits until the reconciler resends it minutes later. This is why `run_after` is skipped for a job that has never been tried.

For the lease, the same bug is much more expensive: two workers with different clocks can decide differently whether the same job's lease has expired. Computing the lease fully in the database leaves a single clock that decides.

The same rule is also written for the queue side in `QUEUE_STANDARDS.md` QUEUE-16.

**Check:** Code review. For every value produced in the application and compared with `now()` in SQL, ask: "Does clock skew change this result?" `test/job-processing.e2e-spec.ts`: a new job is taken at once even if the API's clock is ahead, and a retry's delay is on the database clock.

## Data rules

### DB-22: Data rules are also written in the database

**Rule:** Rules that data must always satisfy are written in the database in addition to the application code:

- **CHECK constraint:** value ranges and consistency between columns. Examples: `users_balance_non_negative` (`balance >= 0`), `jobs_failed_has_error_code`, `jobs_processing_has_lease`, `jobs_finished_at_matches_status`, `user_credit_ledger_job_id_matches_entry_type` (only a `grant` entry has no job), `job_exports_ready_has_file`, `job_outbox_messages_one_subject` (an outbox row names exactly one of a job and an export).
- **Unique and partial unique index:** "at most one" rules (DB-23, DB-24; `job_exports_one_active_per_user_idx`: one unfinished export per user).

The Prisma schema cannot express these, so they are written in the migration SQL. The comment at the top of the Prisma schema file states that the constraints are in the migration. A constraint name starts with the table name and describes the rule.

**Why:** The application code already enforces the rules, but code runs in several places and several processes: the API, the worker, the reconciler, the seed script and a manually run fix query. A single bug in one of them silently writes corrupt data without a constraint, and the corruption is noticed weeks later. A constraint rejects the bad write at that moment and rolls back the transaction. For money bugs, such as the balance going negative, this is the last line of defence.

Constraints between status and columns (a completed job has a `result_source`, a failed job has an `error_code`) guarantee that a row is consistent when read on its own. Reports and the CSV export can depend on this assumption.

**Check:** Code review. When a new column is added, the DB-13 scope note states whether a CHECK constraint is needed.

### DB-23: The balance changes with the ledger, the ledger is append-only

**Rule:**

- The user's `balance` and `reserved` columns change only together with a ledger entry (`user_credit_ledger`). Both are written in a single SQL statement: `WITH ... UPDATE users ... RETURNING` followed by `INSERT INTO user_credit_ledger ... SELECT ... FROM <updated>`. Only `UsersService` makes these writes.
- The ledger is append-only. Its rows are not updated or deleted, and the table has no `updated_at` (DB-04).
- The balance can always be recomputed from the ledger:
  - `balance = grant - reserve + release`
  - `reserved = reserve - capture - release`
- Each job has at most one reserve (`user_credit_ledger_reserve_once_idx`) and at most one capture or release (`user_credit_ledger_settle_once_idx`). Both are partial unique indexes on `job_id`.

**Why:** Keeping the balance as a single number is fast: a reserve is a single-row conditional update (DB-14), and reading the balance does not need summing the ledger. But a single number does not tell the history. When a user asks "where did my credit go", or when a bug corrupts the balance, the answer is only in the ledger. Writing both in the same statement makes it impossible for one to be written without the other.

Being append-only makes the ledger a reliable record: a bug can add a new wrong row but cannot change old correct rows. A correction is also made with a new entry.

The partial unique indexes prevent, at the database level, credit from being captured or released twice, even in a bug such as two workers finishing the same job at the same time. The second write hits the index and the transaction is rolled back. This is the second line of defence behind the ownership token (DB-15).

**Check:** Code review. The tests (TEST-09) and `verify balances` on the running stack check that every user's balance matches the ledger.

### DB-24: A job that must not repeat claims a unique key in its first step

**Rule:** Where the same request or the same content must not be processed twice, the first write of the transaction claims a unique key with `INSERT ... ON CONFLICT DO NOTHING RETURNING`:

- **Idempotency key** (`JobIdempotencyService.claim`): `(user_id, idempotency_key)` is the primary key. If a row is returned, the key belongs to this request and the job is created. If not, the earlier request's record is read: if the body is the same, the earlier job is returned; if the body is different, 422 is returned; if it has expired, the record is deleted and the claim is tried again.
- **Content row** (`JobContentsService.upsert`): `(job_type_code, content_hash)` is unique. The jobs of all users who send the same content share a single row.

The idempotency key's `job_id` foreign key is `DEFERRABLE INITIALLY DEFERRED`: the key is written before the job row it points to, and the foreign key check is done at commit. Keys are valid for 24 hours (`expires_at`), and a background job deletes expired ones (DB-25).

If the request is rejected (such as for insufficient credit), the transaction is rolled back and the key is rolled back too. The user can retry with the same key after adding credit.

**Why:** When two concurrent requests arrive with the same key, the second one's `INSERT` waits on the unique index for the first transaction's outcome. Because the claim is the first step, the second request has done no work while waiting: it has not inserted content and has not locked the user's row. When the first commits, the second request reads the earlier job and returns it. If the first is rolled back, the second request claims the key. Reading first and then inserting ("does the key exist?") would not close this race: both requests would see "no" and create two jobs.

`DO NOTHING` is used instead of `ON CONFLICT DO UPDATE`, because there is no need to change the existing row, and writing an empty update on every conflict grows the table for nothing.

The `DEFERRABLE` foreign key keeps the order correct: the key can be claimed in the first step without waiting for the job row, but no key without a matching job can remain at commit.

**Note:** In `Read Committed`, each statement runs with its own snapshot. If `INSERT ... ON CONFLICT DO NOTHING` waits for another transaction to commit and finds a conflict, a `SELECT` in the same statement may not see that new row. So content insert and key claim are retried a limited number of times with a new statement if the row is not found (`MAX_CONTENT_UPSERT_ATTEMPTS`, `MAX_KEY_CLAIM_ATTEMPTS`). If the attempts run out, 409 `CONFLICT` is returned.

**Check:** `test/jobs.e2e-spec.ts`: 10 concurrent requests with the same key create one job and one reserve; a rejected request can be retried with the same key after credit is added; an expired key creates a new job.

## Scale

### DB-25: Batch jobs run with SKIP LOCKED, in batches

**Rule:** Background jobs that run at the same time in several processes (the reconciler, the outbox relay, idempotency key cleanup) take rows like this:

- `FOR UPDATE SKIP LOCKED`: a row locked by another process is not waited for. It is skipped.
- `LIMIT`: a limited number of rows at a time (`RECONCILER_BATCH_SIZE = 100`, `OUTBOX_RELAY_BATCH_SIZE = 500`, `KEY_CLEANUP_BATCH_SIZE = 1000`).
- `ORDER BY` and index: the selections of the reconciler and the outbox relay read from a partial index that holds only pending rows (`jobs_locked_until_processing_idx`, `jobs_dispatched_at_queued_idx`, `job_outbox_messages_pending_idx`). Idempotency key cleanup reads the plain `job_idempotency_keys_expires_at_idx` index. Its condition depends on `now()`, which a partial index cannot contain.
- While a locked row is changed, the selection condition is checked again (`requeueExpired`, `failStuck`). If the condition no longer holds, the row does not change.

These jobs run in every worker. There is no separate scheduler or leader election (`QUEUE_STANDARDS.md`, QUEUE-14, QUEUE-15). Retention periods are in QUEUE-17.

**Why:** `SKIP LOCKED` lets several workers share work from the same list without waiting for locks: each worker takes different rows. This means that as scale grows, adding workers also adds reconciler and relay capacity. Having no leader election also removes the risk of work stopping when the leader crashes.

The batch size limits how long a transaction holds locks and how much WAL it produces. The partial index holds only pending rows and stays small even when the table reaches millions of finished jobs. The reconciler query that runs every few seconds stays fast regardless of the table's size.

The condition must be checked again, because a job may have moved on through another path between being selected and being changed.

**Check:** Code review. `test/job-processing.e2e-spec.ts` (reconciler), `test/job-idempotency-cleanup.e2e-spec.ts` (cleanup).

### DB-26: List queries are paginated with a cursor and verified with a realistic volume

**Rule:** List and export queries:

- Are paginated with a cursor: the next page continues from the `id` of the last row (`id < cursor`, `ORDER BY id DESC`). `OFFSET` is not used (`API_STANDARDS.md`, API-07).
- Rely on an index made of the same columns as the filter and the sort: `(user_id, id DESC)`, and `(user_id, status, id DESC)` for the status filter.
- Do not select large text in list rows (`JOB_LIST_SELECT`: no input and no result).

A new list query or index is verified with `EXPLAIN ANALYZE` on seed data (`docker compose run --rm seed`). The seed creates 500,000 jobs for a single user and, around it, 5,000 users with 100 jobs each, and runs `VACUUM (ANALYZE)` at the end.

**Why:** `OFFSET 100000` makes PostgreSQL read and discard 100,000 rows. The query gets slower as the page gets deeper. A cursor goes directly to the right place in the index, and every page has the same speed. Also, if new jobs are added between pages, `OFFSET` shifts rows and shows them again; a cursor does not. The ID is a UUID v7, so `id` order is creation order (DB-03) and no separate `created_at` index is needed.

Verification must be done with realistic data, because PostgreSQL's plan depends on the data distribution. If the table has a single user, every row matches the filter and the planner may choose a plan that only works well in that case (scanning the primary key backwards). When other users are added, the plan production will see shows up. `VACUUM (ANALYZE)` updates the planner's statistics after a bulk load and fills the visibility map. Without these, `EXPLAIN` shows a plan that would not happen in reality.

**Check:** Code review. A PR that adds a new list query contains the `EXPLAIN ANALYZE` output.

### DB-27: Frequently updated rows are kept narrow

**Rule:** Rows whose status changes often hold only the status, not the text. The `jobs` table holds the job's status, ownership and price. The input and result text are in the `job_contents` table, and all jobs with the same content share this row. Text columns are compressed with `lz4`.

**Why:** When PostgreSQL updates a row, it writes a new copy of the row. A job is updated many times in its life: claim, every heartbeat, retry, finish. Texts shorter than a few kilobytes stay inside the row and are copied again on every update. Keeping the text in a separate table reduces every update to writing a small row and reduces bloat in the table and its indexes.

List queries also benefit from narrow rows: more jobs fit on the same disk page. The shared content row stores the text once for thousands of users who send the same text, and writes the result (CACHE-05) once. `lz4` compresses and decompresses faster than `pglz`, the PostgreSQL default.

**Check:** Code review. No text column is added to the `jobs` table.
